# Kaggle Dataset Technical Specification

## 1. Overview & Architecture

This specification details the design, pipeline architecture, feature engineering definitions, and validation guarantees for the **IBM AML Stateful Behavioral Feature Engineering Kaggle Dataset**.

The dataset is generated by consuming the core production preprocessing pipeline from `ml-anomaly-engine/preprocessing/` without code duplication or logic modification.

---

## 2. Pipeline Architecture & Data Flow

```
[Raw Source Files]
 ├── HI-Small_Trans.csv (~475 MB)
 └── LI-Small_Trans.csv (~650 MB)
         │
         ▼
 [kaggle/dataset/scripts/build_kaggle_dataset.py]
         │
         ├── Chunk Ingestion (250,000 rows / batch)
         ├── Production FeaturePipeline Instantiation
         ├── AccountState Management (Welford's Algorithm)
         ├── Chronological Order Preservation
         └── Parquet Table Streaming (PyArrow)
         │
         ▼
 [kaggle/dataset/outputs/training_dataset_hi_li_small.parquet]
         │
         ▼
 [Stratified Train / Validation / Test Splitting]
         ├── train.parquet (70%)
         ├── valid.parquet (15%)
         └── test.parquet  (15%)
         │
         ▼
 [kaggle/dataset/validation/validate_dataset.py]
         ├── Schema Verification
         ├── Null Value Check
         ├── Fraud Class Ratio Reporting
         └── SHA256 Checksum Generation
```

---

## 3. Dataset Generation Process

1. **Chunk Processing**:
   - Both raw CSV files are read sequentially in 250,000-row chunks using `pandas.read_csv`.
   - Chronological transaction ordering per account is enforced within `FeaturePipeline.process_dataframe()`.

2. **Stateful Feature Extraction**:
   - `FeaturePipeline` maintains an in-memory map of `AccountState` objects indexed by sender `Account`.
   - Features are computed using only the state prior to the transaction.
   - Account state is updated after transaction feature vector generation.

3. **Stratified Train / Validation / Test Splitting**:
   - `sklearn.model_selection.train_test_split` is applied with `random_state=42` and `stratify=df['is_fraud']`.
   - Splitting ratio: 70% Train, 15% Validation, 15% Test.

---

## 4. Leakage Prevention Strategy

- **Temporal Order**: Transactions are evaluated sequentially in historical time order.
- **Pre-Transaction Evaluation**: Features for transaction $t_n$ rely exclusively on transactions $t_1, t_2, \dots, t_{n-1}$.
- **Post-Transaction Update**: State mutation (`AccountState.update_after_transaction()`) occurs strictly after feature vector output for $t_n$.

## 5. Required Production Features Schema

| Feature Name | Category | Type | Description |
| :--- | :--- | :--- | :--- |
| `amount` | Monetary | `float64` | Transaction payment amount |
| `spending_deviation_score` | Monetary | `float64` | Welford spending Z-score relative to account history |
| `hour` | Temporal | `int64` | Hour of transaction execution (0–23) |
| `day_of_week` | Temporal | `int64` | Day of week (0 = Monday, 6 = Sunday) |
| `month` | Temporal | `int64` | Month of year (1–12) |
| `is_weekend` | Temporal | `int64` | Weekend transaction indicator (1 = Saturday/Sunday, 0 = Weekday) |
| `time_since_last_transaction` | Temporal | `float64` | Elapsed seconds since sender's prior transaction |
| `velocity_score` | Temporal | `int64` | Sender's historical transaction count prior to current event |
| `is_first_transaction` | Temporal | `int64` | Indicator if sender's first transaction (1 = Yes, 0 = No) |
| `is_new_receiver` | Relationship | `int64` | Flag indicating if receiver account is new for sender |
| `is_new_bank` | Relationship | `int64` | Flag indicating if target bank ID is new for sender |
| `is_new_payment_format` | Relationship | `int64` | Flag indicating if payment format is new for sender |
| `is_cross_bank_transfer` | Relationship | `int64` | Indicator if sender bank != receiver bank |
| `is_cross_currency_transfer` | Relationship | `int64` | Indicator if payment currency != receiving currency |
| `payment_channel` | Transaction | `string` | Payment method format (e.g. ACH, Wire, Credit Card, Cheque) |
| `is_fraud` | Target | `int64` | Ground truth label (1 = Laundering, 0 = Legitimate) |

---

## 6. Output Artifacts

All outputs reside in `kaggle/dataset/outputs/`:

1. `training_dataset_hi_li_small.parquet`: Combined full processed dataset (~222 MB Snappy Parquet).
2. `train.parquet`: 70% stratified training split (~162 MB).
3. `valid.parquet`: 15% stratified validation split (~35 MB).
4. `test.parquet`: 15% stratified test split (~35 MB).
